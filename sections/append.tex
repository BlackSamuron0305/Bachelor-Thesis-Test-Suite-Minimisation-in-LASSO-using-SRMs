\section{Scoring Methodology}

To enable systematic comparison, each algorithm is evaluated on criteria C2--C6 using a binary pass/fail system based on LASSO's operational requirements. Criterion C1 (SRM Compatibility) is treated as a mandatory precondition: algorithms that fail C1 are excluded from further evaluation.

\subsection*{Binary Scoring System}

Each criterion is scored as follows:

\begin{itemize}
  \item \textbf{1 (Pass):} Algorithm satisfies LASSO's requirement for this criterion based on literature evidence and theoretical analysis.
  \item \textbf{0 (Fail):} Algorithm does not satisfy the criterion or evidence is insufficient.
\end{itemize}

\subsection*{Total Score Calculation}

The total score is the sum across C2--C6 (maximum 5 points):

\begin{equation}
  \text{TotalScore}(A) =
  \begin{cases}
    0, & \text{if algorithm } A \text{ fails C1 (SRM compatibility)}, \\[3pt]
    \displaystyle\sum_{i=2}^{6} s_i(A), & \text{otherwise, where } s_i(A) \in \{0,1\}.
  \end{cases}
\end{equation}

This binary system reflects LASSO's actual decision requirements: algorithms must be SRM-compatible (C1), preserve coverage (C2) and mutation score (C4), achieve meaningful reduction (C3), scale to production systems (C5), and integrate feasibly (C6). Partial satisfaction is treated as failure.

\subsubsection*{C1 Summary}

C1 enforces SRM-only operation without CFG or AST access and is therefore essential for LASSO's language-agnostic architecture. All matrix-based techniques considered in the literature—greedy heuristics, ILP/SAT/NEMO, metaheuristics and similarity-based approaches—evaluate candidate test suites purely via test--requirement (coverage or mutant) vectors and thus satisfy this precondition~\cite{harrold1993,yoo2012,noemmer2020,khan2020,wei2017}. REDUNET is the only exception because it is explicitly designed to exploit control-flow graph structure to detect redundancy~\cite{mongiovi2020}, which is not available in LASSO's SRM abstraction. Consequently, REDUNET is filtered out after C1 and not considered in the remaining criteria.

\subsubsection*{C2 Summary}

Greedy and exact approaches enforce coverage preservation by construction: greedy algorithms continue selecting tests until each requirement column is covered at least once~\cite{harrold1993,yoo2012,noemmer2020,jehan2023}, and ILP/SAT/NEMO encode the same condition as hard constraints in their optimisation models~\cite{elbaum2002,lin2018}. This matches how these techniques are used in empirical studies, where 100\% structural coverage of the original suite is treated as a non-negotiable adequacy condition~\cite{noemmer2020,jehan2023}. In contrast, search-based and similarity-based methods typically treat coverage as one optimisation objective among several (e.g.\ cost, time budget, multi-objective fitness)~\cite{yoo2012,khan2020,wei2017,bach2017}, so high coverage is encouraged but not guaranteed. Under LASSO's requirement that the minimised suite must retain all structural coverage, only the greedy and exact methods pass C2.

\subsubsection*{C3 Summary}

All greedy, exact and metaheuristic approaches comfortably meet LASSO's 45\% reduction target. Empirical studies on Java programs report suite-size reductions around 69\% for HGS and around 72--74\% for EHGS and GRE on the FIRST RUN benchmark~\cite{gladston2015}, while Noemmer and Haas and Jehan and Wotawa observe roughly 60--75\% reduction for several greedy variants on Java and JavaScript projects~\cite{noemmer2020,jehan2023}. Exact ILP/SAT and NEMO models compute minimal or near-minimal hitting sets for the instances they can solve~\cite{elbaum2002,lin2018}. Search-based techniques such as GAs, MOEAs, PSO and ABC achieve similarly substantial reductions in their case-study evaluations~\cite{yoo2012,wei2017,ahuja2024}. In contrast, similarity-based methods in industrial settings are tuned to maximise coverage under strict time budgets rather than to shrink suites aggressively~\cite{bach2017}, leading to more conservative reductions that do not directly target strong minimisation.

MA-EHGS extends EHGS by treating mutants as explicit requirements. Multi-criteria extensions in prior work show minimal impact on reduction effectiveness: Lin et al.'s tie-breaking variants change reduction by at most 0.3 percentage points~\cite{lin2018}, and Shi et al.\ observe that mutant-based minimisation trades slightly better minimisation for improved fault detection~\cite{shi2018}. We therefore expect MA-EHGS to achieve reduction effectiveness very close to EHGS (70--74\%) while guaranteeing 100\% mutation preservation by design.

\subsubsection*{C4 Summary: The Coverage--Mutation Gap}

Literature demonstrates a consistent gap between structural coverage and mutation score:

\begin{itemize}
  \item Coverage-only minimisation can lead to 3.5--21\% relative mutation loss, especially under aggressive reduction~\cite{noemmer2020}.
  \item When mutants are treated as explicit requirements in the minimisation, mutation loss can be avoided and 100\% of originally killed mutants retained~\cite{jehan2023}.
  \item Many-objective evolutionary algorithms that include mutation score as an explicit fitness objective preserve fault detection while still reducing cost~\cite{wei2017}.
\end{itemize}

Most classical techniques in the tables (greedy, ILP/SAT, PSO, ABC, similarity-based methods) optimise only structural coverage and cost and therefore do not explicitly control mutation score. Only MOEAs~\cite{wei2017} and MA-EHGS model mutants directly: MOEAs treat mutation score as a dedicated objective in a stochastic multi-objective search, whereas MA-EHGS encodes mutants as additional requirements in a deterministic SRM-based greedy algorithm. In LASSO’s setting, MA-EHGS thus bridges the coverage--mutation gap while remaining compatible with the existing SRM infrastructure and scalability requirements.

\subsubsection*{C5 Summary}

Greedy heuristics and similarity-based methods operate in polynomial time over the SRM and have been applied to test suites with thousands of tests and requirements~\cite{yoo2012,noemmer2020,jehan2023,bach2017}. HGS’s original analysis shows a polynomial bound in the number of tests and requirements~\cite{harrold1993}, and EHGS and MA-EHGS follow the same matrix-based pattern~\cite{gladston2015}. In contrast, ILP/SAT formulations inherit the NP-completeness of hitting set~\cite{garey1979} and become costly as problem size grows~\cite{elbaum2002,yoo2012}, while NEMO’s nonlinear formulation is even more computationally demanding~\cite{lin2018}. Population-based algorithms such as GAs, MOEAs, PSO and ABC require many SRM evaluations per generation~\cite{yoo2012,wei2017,ahuja2024}, which makes them orders of magnitude slower in reported case studies. For LASSO’s expected SRM sizes (hundreds of tests, up to thousands of requirements), polynomial-time SRM-based algorithms such as MA-EHGS are therefore much more appropriate.

\subsubsection*{C6 Summary}

From an engineering perspective, SRM-based greedy heuristics are the easiest to integrate: they require only in-memory matrix operations, deterministic control flow and, at most, a few scalar parameters~\cite{harrold1993,gladston2015,yoo2012}. \chapter{Mutation-Aware Enhanced HGS Pseudocode}
\label{app:pseudocode}

This appendix provides precise pseudocode for the Mutation-Aware Enhanced HGS (MA-EHGS) algorithm, which extends the Enhanced HGS (EHGS) heuristic~\cite{gladston2015} with explicit mutation-awareness to address the coverage--mutation gap observed in empirical studies~\cite{noemmer2020,jehan2023}. MA-EHGS operates directly on LASSO's Stimulus-Response Matrix (SRM) representation without requiring control-flow graphs or language-specific program structures, maintaining compatibility with LASSO's language-agnostic philosophy.

\subsection*{Algorithm Overview}

MA-EHGS retains the two-phase structure of EHGS: Phase~1 identifies and selects essential tests that uniquely cover any requirement (structural or mutation), ensuring no loss of coverage. Phase~2 applies a weighted greedy heuristic to select additional tests until all requirements are satisfied. The key innovation is the integration of mutation requirements into the unified requirements matrix $R = R_{\text{struct}} \cup R_{\text{mut}}$ and a weighted scoring function that balances structural coverage and mutation preservation during greedy selection.

By treating both structural coverage (lines, branches, methods) and mutation requirements (killed mutants) as mandatory SRM columns, MA-EHGS guarantees 100\% preservation of both adequacy dimensions while achieving reduction effectiveness comparable to coverage-only EHGS~\cite{gladston2015}. The algorithm operates in polynomial time $O(nq)$, where $n$ is the number of tests and $q$ the total number of requirements, ensuring scalability for LASSO's large-scale analysis requirements.

\subsection*{Notation}

\begin{itemize}
  \item $T = \{t_1,\dots,t_n\}$: set of tests (SRM rows).
  \item $R_{\text{struct}} = \{r_1,\dots,r_m\}$: structural requirements (lines, branches, methods covered).
  \item $R_{\text{mut}} = \{m_1,\dots,m_p\}$: mutation requirements (mutants killed by the original suite).
  \item $R = R_{\text{struct}} \cup R_{\text{mut}}$: unified requirement set (SRM columns).
  \item $M \in \{0,1\}^{n \times |R|}$: binary requirements matrix; $M_{ij} = 1$ iff test $t_i$ satisfies requirement $r_j$.
  \item $R_i = \{r_j \in R \mid M_{ij}=1\}$: set of requirements satisfied by test $t_i$.
  \item Weights: $\alpha \in [0,1]$ for structural requirements, $\beta \ge 0$ for mutation requirements (default: $\alpha = 0.3$, $\beta = 0.7$). Setting $\beta = 0$ recovers purely coverage-based EHGS; setting $\alpha = 0$ prioritises mutation-only selection.
\end{itemize}

\subsection*{Algorithm}

\begin{framed}
\noindent\textbf{Procedure} MAEHGS($M$, $\alpha$, $\beta$)\\
\textbf{Input:} Requirements matrix $M \in \{0,1\}^{n \times |R|}$, weights $\alpha \in [0,1]$, $\beta \ge 0$\\
\textbf{Output:} Minimised test subset $S \subseteq T$ guaranteeing 100\% coverage of all requirements in $R$\\[4pt]

\noindent\textbf{Phase 1: Essential Test Selection}\\
\emph{Objective:} Identify and select all tests that uniquely cover at least one requirement. These tests are essential because omitting them would leave requirements uncovered.\\[4pt]

1. For each requirement $r_j \in R$, compute its set of covering tests:
\[
  T_j = \{ t_i \in T \mid M_{ij} = 1 \}, \quad |T_j| = \text{cardinality of }T_j
\]

2. Initialise selected tests and uncovered requirements:
\[
  S \leftarrow \emptyset,\quad R_{\text{uncov}} \leftarrow R
\]

3. For each requirement $r_j \in R$ with $|T_j| = 1$ (uniquely covered):
\begin{itemize}
  \item Let $t_i$ be the unique test in $T_j$.
  \item Add $t_i$ to $S$ (if not already selected).
  \item Remove all requirements covered by $t_i$ from the uncovered set:
  \[
    R_{\text{uncov}} \leftarrow R_{\text{uncov}} \setminus R_i
  \]
\end{itemize}

\emph{Outcome:} All essential tests are selected. If $R_{\text{uncov}} = \emptyset$, the algorithm terminates (rare in practice). Otherwise, proceed to Phase~2.\\[8pt]

\noindent\textbf{Phase 2: Weighted Greedy Selection}\\
\emph{Objective:} Iteratively select tests that maximise a weighted combination of new structural coverage and new mutation kills, continuing until all requirements are satisfied.\\[4pt]

4. While $R_{\text{uncov}} \neq \emptyset$:
\begin{itemize}
  \item For each test $t_i \in T \setminus S$:
  \begin{itemize}
    \item Compute new structural coverage:
    \[
      \text{newCov}_{\text{struct}}(t_i) = R_i \cap R_{\text{uncov}} \cap R_{\text{struct}}
    \]
    \item Compute new mutation kills:
    \[
      \text{newCov}_{\text{mut}}(t_i) = R_i \cap R_{\text{uncov}} \cap R_{\text{mut}}
    \]
    \item Compute weighted score:
    \[
      \text{Score}(t_i) = \alpha \cdot |\text{newCov}_{\text{struct}}(t_i)| + \beta \cdot |\text{newCov}_{\text{mut}}(t_i)|
    \]
  \end{itemize}
  
  \item Select the test with maximal score:
  \[
    t_{i^*} = \arg\max_{t_i \in T \setminus S} \text{Score}(t_i)
  \]
  \emph{Tie-breaking:} If multiple tests achieve the same score, select the test with the highest total number of newly covered requirements $|\text{newCov}_{\text{struct}}(t_i)| + |\text{newCov}_{\text{mut}}(t_i)|$. If ties remain, use deterministic ordering (e.g., lexicographic by test identifier) to ensure reproducibility.
  
  \item Add $t_{i^*}$ to $S$.
  
  \item Update uncovered requirements:
  \[
    R_{\text{uncov}} \leftarrow R_{\text{uncov}} \setminus R_{i^*}
  \]
\end{itemize}

5. Return $S$.
\end{framed}

\subsection*{Key Properties}

\begin{itemize}
  \item \textbf{Correctness:} By construction, $S$ covers all requirements in $R$. Phase~1 ensures no uniquely-covered requirement is lost. Phase~2 continues until $R_{\text{uncov}} = \emptyset$.
  
  \item \textbf{Determinism:} The implementation uses deterministic data structures (LinkedHashMap, LinkedHashSet in Java) and consistent tie-breaking rules, ensuring reproducible results across executions.
  
  \item \textbf{Language-agnostic:} The algorithm operates solely on the binary matrix $M$, which is constructed from LASSO's SRM representation. No control-flow graphs, abstract syntax trees, or other language-specific structures are required.
  
  \item \textbf{Parameter sensitivity:} Empirical validation (Appendix~\ref{app:benchmarks}) shows that balanced settings ($\alpha, \beta > 0$) produce robust results. Edge cases with $\alpha = 0$ or $\beta = 0$ reduce to mutation-only or coverage-only selection, respectively.
\end{itemize}

\chapter{SRM Coverage Extraction Specification}
\label{app:srm}

This appendix specifies how LASSO’s Stimulus--Response Matrices (SRMs) are converted into a requirements matrix suitable for MA-EHGS.

\section*{SRM Structure}

LASSO stores SRMs in an Apache Ignite distributed cache:

\begin{itemize}
  \item \textbf{Rows (stimuli):} test sequences, method invocations, or API calls.
  \item \textbf{Columns (systems):} executable systems under test.
  \item \textbf{Cells:} structured response objects $M_{ij}$ with execution results for system $j$ responding to stimulus $i$.
  \item \textbf{Cache keys (CellId):} include \texttt{executionId}, \texttt{systemId}, \texttt{adapterId}, \texttt{variantId} (original/mutant), \texttt{sheetId} (test or coverage key), and coordinates.
  \item \textbf{Cache values (CellValue):} include execution outputs, coverage elements, or metrics.
\end{itemize}

\section*{Per-Test Coverage Collection}

Per-test coverage is collected via test lifecycle hooks:

\begin{enumerate}
  \item \textbf{Before each test $t_i$:} coverage counters are reset.
  \item \textbf{During $t_i$:} JaCoCo instruments bytecode and records line, branch, and method coverage.
  \item \textbf{After $t_i$:} coverage data are exported for that test only.
\end{enumerate}

Coverage is stored as cells with a uniform naming scheme, e.g.\ \texttt{sheetId = "COVERAGE\_testName"} and a type field indicating whether the value is a line, branch, or method identifier. This design is language-agnostic and can be mirrored for non-Java systems using other coverage tools.

\section*{Mutation Result Collection}

For mutation testing:

\begin{itemize}
  \item Each test $t_i$ is executed against the original system and each mutant variant.
  \item Results are stored with \texttt{sheetId = "testName()"}, and \texttt{variantId} distinguishing original vs.\ individual mutants.
  \item A mutant is considered \emph{killed} by $t_i$ if any SRM cell for $t_i$ and that mutant differs from the original system’s output in the corresponding cell.
\end{itemize}

\section*{Requirements Matrix Construction}

The SRM data are then transformed into a unified requirements matrix:

\begin{itemize}
  \item Tests $T = \{t_1,\dots,t_n\}$ are derived from distinct test names.
  \item Structural requirements $R_{\text{struct}}$ are derived from covered lines, branches, and methods across all tests and systems.
  \item Mutation requirements $R_{\text{mut}}$ are derived from the set of mutant identifiers killed by at least one test and selected for preservation.
  \item For each test $t_i$ and requirement $r_j$, $M_{ij}=1$ if $t_i$ covers $r_j$ (structural) or kills $r_j$ (mutant). Otherwise $M_{ij}=0$.
\end{itemize}

The resulting matrix $M$ is the input to MA-EHGS and to other SRM-based minimisation algorithms.
