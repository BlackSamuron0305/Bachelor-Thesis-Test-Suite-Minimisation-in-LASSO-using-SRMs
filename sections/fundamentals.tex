\chapter{Fundamentals}\label{chap:fundamentals}

This chapter establishes the theoretical foundation by introducing core concepts and formal definitions required for test-suite minimisation. We present metrics quantifying test-suite effectiveness, describe the \emph{Stimulus--Response Matrix} (SRM) representation within LASSO, and formally define the minimisation problem.

\section{Test Coverage and Mutation Score}

\emph{Test coverage} quantifies the proportion of program elements exercised by a test suite~\cite{zhu1997}. Coverage metrics indicate structural thoroughness but provide limited insight into fault-detection capability.

\subsection{Coverage Metrics}
Coverage criteria define program ``parts'' at different granularity levels~\cite{zhu1997}. Common coverage types in test-suite evaluation:

\begin{itemize}
  \item \textbf{Instruction Coverage:} proportion of bytecode instructions executed (finest-grained, virtual machine level).
  \item \textbf{Line Coverage:} proportion of source lines executed (intuitive source-code feedback).
  \item \textbf{Branch Coverage:} proportion of conditional branches whose true/false outcomes both execute.
  \item \textbf{Method Coverage:} proportion of methods invoked at least once.
  \item \textbf{Complexity Coverage:} proportion of independent execution paths exercised (cyclomatic complexity).
  \item \textbf{Class Coverage:} proportion of classes instantiated or whose static methods execute (coarse-grained).
\end{itemize}

Multi-level coverage captures execution at different granularities. Different types detect different fault classes~\cite{zhu1997}---high line coverage with low branch coverage may miss conditional faults; high method coverage without complexity coverage may miss execution paths in complex methods. Employing metrics across the spectrum from instruction-level to class-level provides complete quality assessment.

\subsection{Mutation Score}

\emph{Mutation testing} quantifies test-suite effectiveness by measuring detection of artificially introduced faults (\emph{mutants})~\cite{jia2011}. Each mutant is a slightly modified version (replacing operators, altering conditionals, modifying constants). Test suites execute against both original and mutated versions.

The \emph{mutation score} expresses the proportion of mutants detected by the test suite and is defined as:
\[
\text{Mutation Score} = \frac{\text{Number of mutants killed}}{\text{Total number of mutants}} \times 100\,\%.
\]
A mutant is considered \emph{killed} when a test detects the introduced fault. The detection criterion depends on the mutation testing approach. Conversely, if a test does not detect the fault, the mutant \emph{survives}.

\paragraph{Mutation Types.}
Two main types of mutation testing are commonly distinguished~\cite{offutt2000}:
\begin{enumerate}
  \item \textbf{Weak Mutation:} a mutant is detected if the program's internal state immediately after executing the mutated statement differs from that of the original program. Detection is based on inspecting local state divergence rather than final output, without requiring the test to fail.
  \item \textbf{Strong Mutation:} a mutant is detected only if the internal divergence propagates to the program's externally observable behaviour, such as output values or test verdicts. This requires execution to completion and comparison of final results, typically causing the test to fail on the mutant while passing on the original program.
\end{enumerate}

Weak mutation focuses on local sensitivity to code changes, while strong mutation measures externally visible behavioural differences. Both flavours aim to approximate a test suite's fault-detection capability, with the mutation score serving as a quantitative indicator of test effectiveness.


\section{Stimulus--Response Matrices}\label{sec:srm}

Stimulus--Response Matrices (SRMs) constitute LASSO's central data structure for \emph{Test-Driven Software Experimentation}~\cite{Kessel2022}, providing unified, language-independent format for recording and comparing run-time behaviour under controlled conditions. SRMs require two input artefacts: \emph{Sequence Sheets} and \emph{Actuation Sheets}.

\subsection{Sequence Sheets and Actuation Sheets}

\textbf{Sequence Sheets} describe ordered stimuli applied to systems under test: tabular, human-readable, directly executable representations bridging code-based unit tests and tabular acceptance tests. Define linear method invocation sequences with input parameters and expected outputs. Notation is language-independent, focusing on behavioural semantics.

Typical columns:
\begin{itemize}
  \item \textbf{Output:} expected result or observable state.
  \item \textbf{Operation:} operation/method name to invoke.
  \item \textbf{Service:} class to instantiate (\texttt{create}) or instance for invocation.
  \item \textbf{Input:} arguments or references to previously created objects.
\end{itemize}

Each row represents one stimulus (method invocation with inputs and expected output). Objects instantiated via \texttt{create}; cell references (e.g., \texttt{A1}, \texttt{D3}) reuse instances. Parameterised sheets introduce placeholders (e.g., \texttt{?p1}, \texttt{?p2}) substituted at runtime for test variants.

\textbf{Actuation Sheets} capture observed responses when executing sequence sheets. Preserve structure but replace expected outputs with actual runtime data, forming \emph{actuation records}. Each record represents one (stimulus, system) execution with concrete inputs and outputs. Sequence sheets describe \emph{intended behaviour}; actuation sheets record \emph{empirical behaviour}. Executing one sequence sheet across multiple systems produces several actuation sheets.

\subsection{From Sequence Sheets to Stimulus--Response Matrices}

LASSO generalises stimuli-to-actuation mapping into multidimensional \emph{Stimulus--Response Matrices} (SRMs), aggregating actuation results of test sets executed across multiple systems/variants:
\[
M = [M_{ij}] \quad \text{with} \quad M_{ij} = \text{Actuation}(t_i, v_j),
\]
where \(t_i \in T\) (stimulus/row), \(v_j \in V\) (system variant/column), \(M_{ij}\) (actuation record with inputs, outputs, analysis attributes).

Core information: input parameters, outputs/return values, exceptions/failures, optional execution traces.

SRMs support \emph{analysis attributes}---key--value pairs storing additional measurements: non-functional metrics (execution time, memory), coverage data (line, branch, method), mutation results/scores, static properties/complexity.

\subsection{Coverage and Mutation Integration in SRMs}

LASSO integrates coverage and mutation data into SRMs. JaCoCo measures structural coverage, reporting entity types (instruction, line, branch, method, class) and metrics (\texttt{COVEREDCOUNT}, \texttt{TOTALCOUNT}, \texttt{COVEREDRATIO})~\cite{jacoco-counters}. Stored as analysis attributes under dedicated \texttt{sheetId} (e.g., \texttt{JACOCO}), enabling fine-grained SRMPATH retrieval.

Mutation analysis: each mutant treated as separate variant \(v_j\). SRM cell \(M_{ij}\) contains mutant actuation. Mutant \emph{killed} if response differs from original:
\[
v_j \text{ is killed by } t_i \iff \text{Response}(t_i, v_j) \neq \text{Response}(t_i, v_\text{orig}).
\]
Comparing responses enables data-driven mutation coverage computation:
\[
\text{Mutation Score} = 
\frac{\text{Number of mutants killed}}{\text{Total number of mutants}} \times 100\,\%.
\]

\subsection{Interpretation and Applications}

SRMs unify execution data (functional outcomes, non-functional metrics, coverage, mutation) into language-independent structure, facilitating regression testing, differential testing, N-version testing, mutation-based assessment. SRMs form LASSO's empirical foundation for optimisation tasks like test-suite minimisation and coverage preservation.








\section{The Test-Suite Minimisation Problem}

Section~\ref{sec:problem-statement} introduced the optimisation goal. This section provides formal definition, computational complexity, and LASSO context.

\subsection{Formal Problem Definition}

Let $T = \{t_1, t_2, \ldots, t_n\}$ denote test suite (stimuli) and $R = \{r_1, r_2, \ldots, r_m\}$ coverage requirements. Each $t_i \in T$ covers subset $C(t_i) \subseteq R$. Full suite coverage:
\[
C(T) = \bigcup_{i=1}^{n} C(t_i).
\]
\emph{Test-suite minimisation problem} seeks smallest subset $S^* \subseteq T$ preserving coverage:
\[
S^* = \arg \min_{S \subseteq T} |S| \quad \text{subject to} \quad C(S) = C(T).
\]
Equivalent to \emph{minimum set-cover problem}.

\subsection{Computational Complexity}

Test-suite minimisation is NP-complete~\cite{yoo2012}; no polynomial-time algorithm guarantees optimal solutions for arbitrary instances. Practical implementations rely on approximation algorithms~\cite{chvatal1979} and heuristics~\cite{harrold1993} trading exactness for scalability. Classical greedy achieves $O(\ln m)$ approximation ratio ($m$ requirements).

\subsection{Test-Suite Minimisation in the LASSO Context}

Within LASSO, minimisation operates on SRM data. Each stimulus $t_i$ corresponds to one SRM row; coverage and mutation attributes stored in response objects $M_{ij}$. Requirement set $C(t_i)$ derived from JaCoCo metrics and mutation results. Objective: select subset $S^* \subseteq T$ preserving full coverage:
\[
C(S^*)_{\text{SRM}} = C(T)_{\text{SRM}}.
\]
Result: reduced SRM containing only selected stimuli.

\subsection{Algorithmic Categories}

Following established classifications~\cite{yoo2012,khan2020,bach2017}, algorithms group into four categories: \textbf{greedy heuristics} (classical greedy, HGS~\cite{harrold1993}), \textbf{exact optimisation} (ILP, constraint-satisfaction~\cite{mongiovi2020}), \textbf{search-based methods} (genetic algorithms~\cite{yoo2012}), \textbf{data-driven methods} (clustering, overlap-aware~\cite{bach2017}). Detailed explanation in Chapter~\ref{chap:literature-review}.
